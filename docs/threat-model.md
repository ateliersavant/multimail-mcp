# Threat model (one page)

Scope: the Worker, its OAuth layer, its Durable Object state, the Google credentials it holds, and the clients that call it. Out of scope: Google's own infrastructure, the end user's device, and the clients' internal security.

## Assets

1. Service-account JSON keys (one per tenant) — the crown jewels: each grants `gmail.modify` over every mailbox in its tenant.
2. Client access and refresh tokens issued by this server.
3. The principal allowlist and the tenant file (which mailboxes exist, which aliases may send).
4. Mail content in transit through the Worker (never stored, never logged).
5. The audit log (metadata only), kept 90 days in D1.
6. The right to send as each company's addresses.

## Threats and controls

| # | Threat | Likelihood | Impact | Controls | Residual |
|---|---|---|---|---|---|
| T1 | Service-account key leaks (repo, laptop, Cloudflare account) | low | **critical** | Keys only in Cloudflare secrets; never on disk after upload; one key per tenant; single scope `gmail.modify`; key-creation org policy respected; rotation runbook; gitleaks in CI and on history before any publication | A leaked key works outside this server, with the scope's full reach: it reads, sends directly and moves mail to Trash across the tenant until rotated. Stated in SECURITY.md. |
| T2 | Client token theft or replay | medium | high | Access tokens short-lived and audience-bound (RFC 8707) to this server; refresh tokens rotate; revocation endpoint; tokens never in URLs | A stolen live access token works until expiry. |
| T3 | Unauthorised person authorises a client | medium | high | Upstream identity is Google sign-in; principal must be in `ALLOWED_PRINCIPALS` (checked on every authorisation and on every MCP call, `email_verified` required); the id_token's `hd` must be the address's own domain or another domain of the same company, so a consumer Google account registered on a company address, or one managed by another Workspace, is refused | None beyond Google account compromise of an allowed principal. Pinning each address to one Google account id was considered and not built: only that Workspace's admin can create a second account for a managed address, and that admin can already reset the existing one. |
| T4 | Prompt injection in an email body makes the model act | **high** | high | Bodies returned as untrusted text, HTML stripped in linear time, no attachment fetch; sender and recipient headers parsed per RFC 5322 with invisible characters removed, so a display name can never hide or fake the real address; drafts are plain text only (the model cannot add an HTML version the human never sees) and `get_draft` shows any HTML part a draft gained elsewhere; every tool description and the server instructions warn the model; there is no direct send, only `send_draft` of a draft the human was shown; label and Trash changes act on one thread or message at a time, cannot touch Spam or Gmail-managed labels, are read back, reversible (Trash for 30 days) and limited, and nothing is deleted permanently; replies only from the mailbox that received the message; no forwarding; no cross-tenant writes; sending limits cap the blast radius; telemetry content-free | The model can still *draft* bad content; the human approval step is the control (see T12). |
| T5 | Cross-tenant leakage | low | **critical** | Every tool takes one `account`; tenant resolved from config only; `from` and reply references outside the tenant refused; domains cannot belong to two tenants (validated at boot); each tenant has its own service account | A model may copy content across two calls. Visible through the `tenant` echo; not preventable server-side. |
| T6 | Send-as spoofing | low | high | `from` must be in Gmail's Send-as list for that mailbox **and** in the operator allowlist; `pending` and unlisted refused; Workspace aliases accepted only on the company's own domains; re-checked at send time on the draft as it is then, read untruncated: exactly one From header naming exactly one mailbox, and no Sender that differs from it; the sent message is read back and a rewritten From is flagged | Relies on Gmail's own Send-as verification. Confirmed live on 2026-11-03 (accepted, pending and unlisted aliases each reported correctly). |
| T7 | Duplicate send after a lost confirmation | medium | medium | Three-state outcome; `failed` only when provably nothing was sent (a 4xx other than 404, or the draft still in Drafts after an ambiguous error); a 404 at send is ambiguous, because the draft may have been sent elsewhere; `sent_unconfirmed` carries the message id and a do-not-resend instruction; an atomic claim in the Durable Object lets exactly one of several concurrent sends of a draft reach Gmail; a durable ledger refuses a later send of a sent draft, and a failure to record the send is reported with it, never as "nothing was sent" | A model that recreates the content as a new draft and the human approves it again; the instruction text and the approval step are the controls. Mutation-tested. |
| T8 | Log or audit leakage | medium | high | Audit module accepts a closed field set and the D1 table has no column that could hold content; error codes are short enums; refused model input (an unknown account, a disallowed From) is not recorded; configuration errors name variables, never values (a tenant-file typo is not echoed into the log); rows deleted after 90 days | Cloudflare account compromise exposes 90 days of metadata (which mailbox sent how many emails, when, from which address). |
| T9 | Dependency or build compromise | low | high | Lockfile pinned; `npm ci`; egress allowlist in code (host, method and exact path for each Google call the server makes) and CI grep; redirects refused; the OAuth library's own fetches (client metadata documents, and the signing keys a document names for client assertions) reachable only through a document on the supported clients' hosts (T14); minimal dependency set | A compromised dependency running inside the Worker could bypass the wrapper and use the global fetch. |
| T10 | Denial of service, quota exhaustion, mass mailing | medium | medium | 120 MCP requests per minute per client token (429 + Retry-After); 10 client registrations per hour per source address; 300 label or Trash changes per hour; 120 drafts per hour and 20 sends per hour / 100 per day per principal across all mailboxes, counted atomically in the Durable Object; bounded pages, bodies, headers and recipients (50); HTML stripping and header parsing in linear time; fail closed on quota errors (never an empty "no mail") | A hijacked client can still send up to the daily limit before it is noticed; the audit log and the emergency stop are the response. |
| T11 | Configuration error (wrong mailbox, typo in alias) | medium | medium | Tenant file validated at boot with unknown-key rejection; refuses to start on any issue; `check:tenants` before deploy | None material. |
| T12 | An AI client sends without real human approval (auto-approved tool calls, a model that skips the preview) | medium | high | No direct send; `send_draft` description demands explicit approval of the exact draft; ChatGPT asks before write tools and Claude shows each tool call; drafts can only come from allowed, Gmail-accepted addresses; sending limits; every send audited with draft, message, From and client | Depends on the client's approval settings and on the human reading the draft. If a connector is set to auto-approve, approval is only as good as the human's attention. |
| T13 | Audit gap: the durable store is unavailable | low | medium | The log stream always receives the record first; a D1 failure is reported by error name and never turns a completed action into an error; the Worker refuses to start without the D1 binding | Records written only to the log stream during a D1 outage are kept for the stream's retention, not 90 days. |
| T14 | Malicious or look-alike OAuth client: open registration, client metadata documents, consent phishing | medium | high | Client metadata documents accepted only from the supported clients' hosts (Claude, ChatGPT; operator-extensible), screened at the Worker entry before the OAuth library could fetch anything; registration accepts only redirect URIs on those hosts or on loopback, and no client key URLs; registrations limited per source address; the consent page shows the client's name and where it returns | A client that is itself compromised on a supported host. The principal allowlist still decides who can finish sign-in. |

## Trust boundaries

- Browser ↔ Worker (sign-in, OAuth redirects): TLS, PKCE, `state`, RFC 9207 `iss`.
- Client ↔ Worker (`/mcp`): bearer tokens, audience validation.
- Worker ↔ Google: service-account JWT assertions minted per request (short-lived), Gmail API over TLS, egress allowlist.
- Operator ↔ Cloudflare: account security is out of scope but decisive for T1 and T8; enable 2FA and restrict API tokens.
- Response: `docs/runbook.md` (emergency stop in seconds, per-company cut-off, key rotation, revoke every token, audit export).

## What would change this model

Adding a second principal (multi-user), attachment handling, forwarding, or a direct-send tool would each reopen T3, T4, T5 and T12 respectively and require a new review.
